# Формат дальнейшей работы

## Регламент

1. План утверждён → делаем **только этап N**, не «заодно этап N+1».
2. Перед этапом — короткий микро-план (файлы, контракты API, критерии приёмки) → ожидание OK.
3. После этапа — отчёт: что сделано, как проверить, что не вошло, какие риски всплыли → ожидание подтверждения.
4. Каждый этап заканчивается правкой `docs/ARCHITECTURE.md` (и `docs/GPU.md` / `docs/RAG.md` по мере появления).
5. Код пишем только после OK на текущий этап.
6. Статус в [README.md](README.md) этой папки обновляется после приёмки этапа.

## Что входит в микро-план этапа

- Список файлов, которые будут созданы или изменены.
- Контракты API (пути, JSON, SSE-события).
- Что сознательно **не** делается на этом этапе.
- Команды проверки и ожидаемый результат.

## Что входит в отчёт этапа

- Сделано (факты, не намерения).
- Как воспроизвести проверку.
- Известные дыры / отложенное.
- Нужно ли менять архитектуру или DECISIONS.

## Порядок этапов

```
0 каркас
    → 1 текст
        → 2 картинка + GPU
            ↘
0 (Qdrant) → 3 RAG → 4 pipeline → 5 NestJS → 6 UI → 7 полировка
    → 8 темы → 9 озвучка → 10 музыка → 11 видео
```

Этап 3 зависит от этапа 0 (Qdrant), не от этапа 2. На практике идём линейно. Этапы 8–11 тоже по одному: следующий файл открываем после приёмки предыдущего.
